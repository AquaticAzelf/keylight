# AK820 Driver Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a portable Windows `.exe` that fully controls an AJAZZ AK820 (USB
`320F:505B`) over HID — lighting, per-key colour, profiles, macros and key remap — with
professional-grade UI and no installer, no registry writes, no cloud.

**Architecture:** Python 3 backend (`ctypes` → `hid.dll`) that speaks the EVision V1
64-byte HID protocol; a loopback HTTP server exposing a JSON API; a vanilla
HTML/CSS/JS front-end rendered in an Edge WebView2 window via `pywebview`, with an
Edge `--app=` fallback. The protocol layer is written against a byte-level spec produced
by a Frida capture of the vendor app, and is unit-testable offline against recorded
packets.

**Tech Stack:** Python 3.14 (stdlib `ctypes`, `http.server`), `pywebview` (WebView2
window), `pyinstaller` (one-file packaging), `frida` (protocol capture only, dev-time),
`pytest` (offline tests), vanilla HTML/CSS/JS (no framework, no CDN, offline).

**Spec:** `docs/superpowers/specs/2026-10-20-ak820-driver-design.md`

## Global Constraints

- Ship one portable `.exe`. No installer, no registry writes, nothing written to
  Program Files, no AppData install. Uninstall = delete the folder.
- The app must work **fully offline**. No CDN links, no web fonts, no network calls in
  shipped code. The backend binds `127.0.0.1` only.
- Front-end is **vanilla HTML/CSS/JS**. No React, no Tailwind, no build step, no npm.
- The keyboard protocol is EVision V1: 64-byte HID output report, report ID `0x04`,
  checksum = `sum(bytes[3..63])` as u16 LE at bytes 1-2, command at byte 3, size at
  byte 4, parameter id at byte 5, offset u16 LE at bytes 5-6, payload at bytes 8-63.
- Lighting parameter: id `0x00`, size 8, payload
  `[mode, brightness, speed, direction, random, R, G, B]`; brightness 0-4, speed 0-5
  (0 = fastest), direction 0-3 = L/R/U/D.
- Mode IDs: `0x01` wave, `0x02` cloud, `0x03` vortex, `0x04` spectrum, `0x05` breath,
  `0x06` static, `0x07` reactive, `0x08` ripple, `0x09` traverse, `0x0A` stars,
  `0x0B` fireworks, `0x0C` roll, `0x0D` wave bar, `0x0E` cartoon, `0x0F` rain,
  `0x10` scan, `0x11` surmount, `0x12` speed, `0x14` custom, `0x00` off.
- Device identity: VID `0x320F`, PID `0x505B`, usage page `0xFF1C`, interface 1.
- The HID handle is opened per transaction and closed again, so other HID tools can
  still open the keyboard.
- The PC-side remap layer uses a `WH_KEYBOARD_LL` hook, is clearly labelled PC-side, and
  is inactive unless the user turns it on.
- Screen colour capture is a one-shot eyedropper, not a live effect.
- PowerShell on this machine is 5.1: no `&&`, `$` mangles inline commands — put
  anything non-trivial in a `.ps1` file.
- `cmd.exe` quoting: no `"` inside a `"`-quoted argument; use single quotes for the
  device-side shell.
- Nothing may be written to the keyboard unless a task explicitly says to.
- Design skills come only from `.opencode/skills/` and must be **recent**: check the
  "Last updated" column in `.opencode/skills/README.md` before loading one, and do not
  add a skill whose own path has not changed in its repo for more than ~3 months
  without asking the owner. Star count is not evidence of currency.
- A UI sub-agent that finds a skill's advice conflicting with this plan follows the
  plan and says so in its final message.

## Review Focus

These are the inputs the spec implies but no test would otherwise catch. Each has a
test pinned to the task that owns the code.

1. **Keyboard unplugged mid-session** — the app must show "not connected" and keep the
   UI usable, and must not crash or spin the CPU. (Task 7)
2. **A second HID tool (the official app, OpenRGB) holds the keyboard open** — our open
   must fail cleanly with a readable message, not hang. (Task 1)
3. **Firmware that rejects a setting** (e.g. a mode id this board does not implement) —
   the app must not present that control at all, and a write must not leave the
   keyboard in a half-configured state. (Tasks 4, 8)
4. **The window is resized down to 1100×720 and up to 2560×1440** — the layout must
   not break, clip the on-screen keyboard, or reflow into unreadable stacking. (Task 8)
5. **A profile is saved on a machine with a different keyboard plugged in** — loading
   it must fail with a clear message, not write garbage to the wrong device. (Task 10)
